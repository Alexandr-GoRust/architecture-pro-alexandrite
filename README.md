# Спринт 6. Кеширование и наблюдаемость — «Александрит»

Проектная работа курса «System Design Pro» (Яндекс Практикум), спринт 6.
Кейс: **«Александрит»** — производство ювелирных украшений на заказ
(конструктор 3D-моделей), онлайн-магазин + CRM + MES, интеграция MES ↔ CRM
через RabbitMQ.

## Состав решения

| Задание | Файл | Суть |
|---|---|---|
| **Task1** | `Планирование: анализ, идентификация проблем и поиск решений.md` | 10 проблемных мест, 8 инициатив с приоритетами, целевая архитектура на полгода, топ-3 инициативы |
| **Task2** | `Выбор и настройка мониторинга в системе.md` | RED для API + USE для инфраструктуры + золотые сигналы для пути заказа; метрики с ярлыками; план внедрения (Prometheus + Grafana); пороги насыщенности и реакции (доп) |
| **Task3** | `Архитектурное решение по трейсингу.md` + `C4_tracing.drawio` + `C4_tracing_alerting.drawio` | Точки риска пути заказа, данные трейсинга, OpenTelemetry + Jaeger; новые элементы на C4 — красным; мониторинг пути заказа и Alertmanager — зелёным (доп) |
| **Task4** | `Архитектурное решение по логированию.md` | INFO-логи пути заказа, уровни, приоритет систем, Filebeat → Logstash → OpenSearch, политика безопасности и хранения, алертинг/аномалии, критерии выбора стека (доп) |
| **Task5** | `Архитектурное решение по кешированию.md` + `caching_sequence.png/.puml` | Кеш дашборда MES (Redis, Cache-Aside), sequence-диаграмма чтения/записи, инвалидация по событию смены статуса + TTL, сравнение стратегий и двух решений (доп) |

## Логика решения

Главная боль бизнеса — потерянные и зависшие заказы. Поэтому ядро плана
(Task1): **наблюдаемость** (Task2–4: метрики, трейсинг, логи) +
**надёжность конвейера сообщений** + **кеш дашборда MES** (Task5) — и только
затем масштабирование и автоматизация релизов.
