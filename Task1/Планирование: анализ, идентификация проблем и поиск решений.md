# Планирование: анализ, идентификация проблем и поиск решений

Кейс: «Александрит» — производство ювелирных украшений на заказ. Три приложения:
онлайн-магазин (Vue + Java Spring Boot), CRM (Vue + Java), MES (React + C#);
MES ↔ CRM через RabbitMQ; каждое приложение и каждая БД — по одному инстансу
(EC2 / Managed БД Yandex Cloud, чтение и запись в один инстанс).

## 1. Проблемные места (существующие и потенциальные)

### Бизнес-симптомы

1. **Заказы теряются и зависают.** Клиенты месяцами ждут обещанных трёх недель;
   представители компаний-партнёров «ежедневно сообщают, что не получили свои
   заказы». Производство при этом не узкое место — мощности готовы к двукратному росту,
   значит проблема в IT-контуре между приёмом заказа и производством.
2. **После открытия API компанию «завалило заказами»** и жалобы выросли —
   нагрузка выросла скачком, а система не масштабируется (по одному инстансу
   на приложение и на БД).
3. **Дашборд MES (первая страница) долго грузится.** Фильтр по статусам и
   пагинация не помогли; операторам критичны самые новые заказы (от этого
   зависит их вознаграждение) — тяжёлое чтение из MES DB на каждый вход.
4. **Потеряны крупные контракты**, недовольство B2C растёт — прямые деньги.

### Технические корни

5. **Нет наблюдаемости.** Подключена только Яндекс Метрика (B2C-веб-аналитика);
   после открытия B2B API она «не даёт полной картины». Ошибки разбираются
   «со слов клиента»; где заказ «сломался» — в магазине, CRM, очереди или MES —
   никто не видит. Нет метрик, логов, трейсинга.
6. **Хрупкая интеграция MES ↔ CRM через RabbitMQ.** Заказ из API-сценария
   создаётся в CRM получением сообщения из очереди — при потере/дубле/ошибке
   обработки сообщения заказ пропадает или зависает в промежуточном статусе.
   Нет идемпотентности, dead-letter-очередей, ретраев и мониторинга глубины
   очередей.
7. **Одиночные точки отказа.** По одному инстансу каждого приложения (EC2) и по
   одной БД на чтение+запись: любой сбой/обновление = простой всей системы;
   вертикальное масштабирование ограничено.
8. **Нет защиты от перегрузки.** Открытый API без rate limiting: пиковый поток
   (а «пиковая нагрузка, как правило, превышает среднюю в два раза») валит
   каскадом магазин → CRM → MES.
9. **Долгий релизный цикл.** Ручной E2E QA + ручной деплой в release/prod,
   задержки релизов растут — исправления проблем не доезжают до прода неделями.
10. **Долгий расчёт стоимости (2–30 мин)** на стороне MES — сам по себе это
    осознанный дизайн (асинхронный расчёт), но без трейсинга клиент и поддержка
    не видят, на какой стадии заказ.

## 2. Инициативы

| № | Инициатива | Что закрывает |
|---|---|---|
| И1 | **Наблюдаемость**: мониторинг (Prometheus + Grafana; RED для API/сервисов, USE для инфраструктуры), централизованное логирование (ELK), трейсинг сквозного прохождения заказа (OpenTelemetry + Jaeger), алертинг | №1, №5, №10 — видим, где теряются и тормозят заказы |
| И2 | **Надёжность интеграции MES ↔ CRM**: идемпотентная обработка сообщений (order_id как ключ дедупликации), DLQ + ретраи, publisher confirms, мониторинг глубины/лагов очередей | №1, №6 — прекращаем потерю сообщений |
| И3 | **Кеширование дашборда MES**: серверный кеш списка «заказов в работе» (Redis, паттерн Cache-Aside/Read-Through + инвалидация по факту изменения статуса) | №3 — быстрая первая страница для операторов |
| И4 | **Устранение SPOF и масштабирование**: read-replica у БД (магазин, CRM, MES db), 2+ инстанса приложений за балансировщиком, RabbitMQ-кластер (кворумные очереди) | №2, №7 |
| И5 | **Защита от перегрузки**: rate limiting на API, Backpressure (ограничение скорости приёма), Circuit Breaker на вызовах MES API | №2, №8 |
| И6 | **Автоматизация релизов**: автотесты (QA хочет автоматизацию, есть прототипы), E2E в CI, автодеплой в release, ручной только прод | №9 |
| И7 | **Единая статусная модель заказа**: сквозной аудит смены статусов (кто/когда/почему), компенсирующие сценарии для «застрявших» заказов | №1, №10 |
| И8 | **Ёмкостное планирование**: нагрузочное тестирование под двукратный рост, план масштабирования БД и очередей | №2 — прогнозируем рост +100 заказов/мес |

## 3. Приоритизация и рассуждения

Порядок расстановки: сначала то, что **останавливает потерю денег** (ушедшие
контракты, зависшие заказы), затем то, что даёт **основу для остальных решений**
(без видимости системы любые доработки вслепую), затем скорость работы
операторов и надёжность, и только потом оптимизация процессов.

**Приоритет 1 — И1 «Наблюдаемость».** Нельзя чинить то, чего не видишь: пока
нет метрик, логов и трейсов, мы не знаем, теряется ли сообщение в очереди,
падает ли обработчик CRM или тормозит MES. Наблюдаемость — фундамент и для
инцидент-менеджмента (сейчас разбор идёт неделями со слов клиентов), и для
проверки эффективности всех следующих инициатив.

**Приоритет 2 — И2 «Надёжность интеграции MES ↔ CRM».** Главный бизнес-симптом
— потерянные/зависшие заказы, а самый вероятный виновник — конвейер сообщений.
Идемпотентность + DLQ + ретраи устраняют сам класс проблемы (потеря и дубли),
мониторинг очередей (из И1) делает остаточные сбои видимыми за минуты.

**Приоритет 3 — И3 «Кеширование дашборда MES».** Операторы — это производство,
которое «готово к двукратному росту»: пока первая страница грузится долго,
операторы не могут быстро забирать новые заказы, и пропускная способность
контура деградирует. Кеш читаемого списка с инвалидацией по факту изменения —
быстрый победимый шаг с ясным эффектом.

**Приоритет 4 — И5 «Защита от перегрузки»**: API уже открыт, следующий пиковый
наплыв может положить систему целиком.

**Приоритет 5 — И4 «SPOF и масштабирование»**: важно, но дороже и длительнее;
текущая нагрузка (даже ×2) выдерживается вертикальным запасом EC2/Managed,
а устойчивость к потере сообщений важнее горизонтального масштабирования.

**Приоритеты 6–8 — И7 (статусная модель и аудит), И6 (автоматизация релизов),
И8 (нагрузочное тестирование)**: улучшают качество жизни и предсказуемость,
влияют на скорость доставки исправлений, но не останавливают текущую утечку
денег напрямую.

## 4. Целевая архитектура через полгода

Три приложения сохраняются (переписывать ничего не нужно), но каждый контур
становится отказоустойчивым и наблюдаемым:

- **Инфраструктура**: приложения — по 2+ инстанса за балансировщиком
  (автоскейлинг при росте); БД каждого домена — запись в мастер + read-replica
  (чтения уходят на реплику, в том числе дашборд MES); RabbitMQ — кластер с
  кворумными очередями, DLQ и идемпотентными консьюмерами.
- **Наблюдаемость**: Prometheus + Grafana (RED-метрики API и сервисов, USE для
  узлов, бизнес-дашборд «путь заказа»), ELK-стек для логов всех приложений,
  OpenTelemetry + Jaeger для сквозного трейсинга заказа по статусам; алерты в
  дежурный канал.
- **Кеширование**: Redis перед MES DB для списка заказов в работе и справочников;
  инвалидация — по событию изменения статуса заказа (программная, по ключу).
- **API**: rate limiting + Backpressure на входе, Circuit Breaker на вызовах
  MES API и внешних расчётчиков.
- **Процессы**: автотесты и E2E в CI, автоматический деплой до release,
  канареечный деплой в прод; поддержка разбирает инциденты по трейсам и логам,
  а не со слов клиентов.

## 5. Если можно выполнить только три пункта за полгода

1. **И1 — Наблюдаемость (метрики + логи + трейсинг).** Единственная инициатива,
   которая превращает все остальные из «догадок» в измеримые проекты: без неё
   мы не сможем ни доказать, где теряются заказы, ни проверить, что починили.
   Кроме того, она сама снижает стоимость инцидентов (MTTR: недели → часы).

2. **И2 — Надёжность конвейера сообщений (идемпотентность + DLQ + ретраи +
   мониторинг очередей).** Прямо останавливает главную утечку денег — потерю
   заказов и, как следствие, уход B2B-контрактов. Реализуется силами existing
   команды (Java + C# разработчики) без смены стека.

3. **И3 — Кеширование дашборда MES (+ перевод тяжёлых чтений на read-replica
   MES DB как подзадачу).** Быстрый измеримый эффект для операторов
   (производство): первая страница загружается за миллисекунды из кеша,
   «самые новые заказы» видны сразу. Read-replica в том же пункте снимает
   нагрузку чтений с основной БД и готовит почву для масштабирования.

Почему не масштабирование/автоскейлинг в тройке: производство и текущая
инфраструктура выдерживают двукратный рост — узкое место не в мощностях, а в
надёжности конвейера и скорости диагностики. Почему не автоматизация релизов:
ускоряет доставку исправлений, но сама по себе не устраняет причины инцидентов,
которые эти исправления порождают.
