# Выбор и настройка мониторинга в системе

Контур: онлайн-магазин (Vue + Java), Shop API, CRM (Vue + Java) + CRM API,
MES (React + C#) + MES API, Messages Queue (RabbitMQ), БД (Shop DB, MES db,
CRM DB — Managed Yandex Cloud), 3d files storage. Инфраструктура — EC2.

## Мотивация

Бизнес-контекст: после открытия B2B API Яндекс Метрика перестала давать полную
картину — она видит только веб-витрину B2C и ничего не знает о заказах,
создаваемых через очередь от MES. При этом компания теряет контракты из-за
заказов, которые «теряются и зависают», а разбор каждой проблемы идёт неделями
со слов клиентов.

Что даст мониторинг:

1. **Обнаружение проблемы раньше клиента.** Сейчас о сбоях узнаём от
   менеджеров и партнёров. Алерты на ошибки/очереди сократят время обнаружения
   с дней до минут.
2. **Диагностика «где сломалось»**: метрики с ярлыками (сервис, эндпоинт,
   статус) покажут, какой из четырёх бэкенд-компонентов деградировал, без
   «допроса» каждого сервера по SSH.
3. **Защита выручки**: дашборд «путь заказа» (сколько заказов в каждом статусе,
   сколько «застряло») делает потерю заказа видимой в момент, когда клиента ещё
   можно удержать.
4. **Обоснование инфраструктурных решений**: данные об утилизации/насыщенности
   — аргумент для масштабирования вместо гаданий.
5. **Дешёвый старт**: сбор метрик — это SDK в приложениях + один инстанс
   стека; стоит несопоставимо меньше одного потерянного B2B-контракта.

## Выбор подхода к мониторингу

Система неоднородна, поэтому применяем **комбинацию подходов**:

| Часть системы | Подход | Почему |
|---|---|---|
| Shop API, CRM API, MES API (HTTP-сервисы, request-driven) | **RED** (Rate, Errors, Duration) | Метрики, важные конечным пользователям и партнёрам API; прямо показывают «сколько запросов, сколько ошибок, сколько длится» |
| Узлы EC2, БД, RabbitMQ, Redis (ресурсы) | **USE** (Utilization, Saturation, Errors) | Ресурсы, деградирующие под нагрузкой: утилизация/насыщенность/ошибки по каждому ресурсу быстро локализуют «железные» bottleneck'ы |
| Сквозной путь заказа (магазин → очередь → CRM → MES) | **Четыре золотых сигнала** (задержка, трафик, ошибки, насыщенность) | Система отдаёт API и является распределённой; золотые сигналы — общий знаменатель для дашборда «здоровье заказа» и аномалий |

Ограничения учтены: RED не подходит для потоковых/фоновых обработчиков — для
консьюмеров очередей используем метрики очередей (глубина, lag, время
обработки сообщения) в духе золотых сигналов.

## Метрики

### A. Слой API — RED (Shop API, CRM API, MES API)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `http_requests_total` (counter) — Rate | Пропускная способность каждого API, пики (пиковая нагрузка ≈ ×2 от средней — на неё и планируем ёмкость) | `service`, `endpoint`, `method`, `status`, `source` (b2c/b2b) |
| `http_errors_total` (counter) — Errors | Доля неудачных запросов; SLA для B2B-партнёров | `service`, `endpoint`, `status` (5xx и бизнес-ошибки отдельно), `source` |
| `http_request_duration_seconds` (histogram) — Duration | Латентность: гистограмма с бакетами даёт перцентили p50/p95/p99; «медленный дашборд MES» виден здесь | `service`, `endpoint`, `method` |

### B. Слой бизнес-логики — путь заказа (золотые сигналы)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `orders_total` (counter) | Создано/переведено заказов; провал «созданий» после открытия API — виден сразу | `status` (INITIATED…CLOSED), `channel` (shop/api), `system` |
| `orders_stuck` (gauge) | Заказы «застряли» в промежуточном статусе дольше SLA — прямой индикатор потерянных заказов | `status`, `age_bucket` |
| `price_calc_duration_seconds` (histogram) | Расчёт стоимости 2–30 мин: контроль длительности и очереди на расчёт | `model_complexity` (бакеты полигонов) |
| `order_lifecycle_seconds` (histogram) | Полное время прохождения статусов — «обещали три недели» превращается в метрику | `from_status`, `to_status` |

### C. Слой очередей — интеграция MES ↔ CRM

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `rabbitmq_queue_depth` (gauge) | Насыщенность: растущая глубина = консьюмер не успевает (насыщенность из золотых сигналов) | `queue`, `vhost` |
| `rabbitmq_messages_published_total` / `consumed_total` (counter) | Баланс публикаций и потребления; расхождение = потери | `queue`, `publisher` (mes/crm) |
| `consumer_processing_seconds` (histogram) | Время обработки одного сообщения (расчёт, запись в CRM) | `consumer`, `message_type` |
| `rabbitmq_dlq_messages_total` (counter) | Попадание в dead-letter — раньше клиента узнаём о битом сообщении | `queue`, `reason` |

### D. Слой инфраструктуры — USE (узлы, БД, кеш)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| CPU utilisation, load average (gauge) | Утилизация EC2-узлов | `instance`, `app` |
| RAM used/available, swap (gauge) | Утилизация/насыщенность памяти (swap = насыщенность RAM) | `instance`, `app` |
| Disk IOPS/throughput/queue depth | Насыщенность диска (критично для БД) | `instance`, `disk`, `db` |
| DB connections in use / pool (gauge) | Насыщенность пула соединений — частая причина «подвисаний» Java-сервисов | `service`, `db` |
| Replication lag (gauge) | Отставание read-replica — устаревшие данные на дашбордах | `db` |
| Redis: ops/sec, memory, hit ratio (gauge/counter) | Здоровье кеша дашборда MES; hit ratio < порога = кеш не работает | `instance`, `cache` |

### E. Метрики из сторонних систем

- **Яндекс Метрика** остаётся источником B2C-веб-аналитики (DAU, конверсии) —
  её данные сводим с бэкенд-метриками на одном дашборде.

## План действий (драфт ТЗ)

1. Поднять инстанс стека мониторинга: Prometheus (TSDB, pull-модель) + Grafana
   (визуализация, алерты); экспортёры: `node_exporter` (EC2), `rabbitmq_exporter`,
   `mysqld/postgres_exporter` (Managed БД), `redis_exporter`.
2. Java-сервисы (магазин, CRM): подключить `micrometer-registry-prometheus`,
   exposes `/metrics`; MES (C#): `prometheus-net`; единый порт 9090/metrics.
3. Внести в `scrape_configs` Prometheus все job'ы (shop-api, crm-api, mes-api,
   инфраструктурные экспортёры); interval 15s.
4. Заложить RED-метрики и бизнес-метрики пути заказа (`orders_total`,
   `orders_stuck`) в код сервисов.
5. Собрать дашборды Grafana: «Общее здоровье» (золотые сигнала по API),
   «Путь заказа» (статусы, застрявшие, время прохождения), «Инфраструктура»
   (USE по узлам/БД), «Очереди».
6. Настроить алерт-правила (см. дополнительное задание) и канал доставки
   (Telegram/e-mail дежурному).
7. Документировать runbook для каждого алерта: что смотреть, где, кто чинит.

## Дополнительное задание: показатели насыщенности, пороги и реакции

| Показатель насыщенности | Порог | Почему | Действие при превышении |
|---|---|---|---|
| RabbitMQ `queue_depth` (интеграционные очереди) | > 1000 сообщений 5 минут | Глубина сверх нескольких минут потока = консьюмеры не успевают, заказы начнут «зависать» | Алерт high → дежурный смотрит консьюмеры; > 5000 — автотикет + оценка включения доп. инстансов консьюмера |
| CPU узла (utilization) | > 80% 10 минут | Выше — деградация латентности, до «смерти» узла остаётся запас на пики ×2 | Алерт → вертикальное расширение/добавление инстанса приложения за балансировщик |
| RAM: swap-in активен | любой устойчивый swap | Память насыщена, ОС свопит — латентность резко растёт | Алерт high → расширение памяти/инстанса, ревизия утечек |
| DB: пул соединений | > 80% пула | Новые запросы ждут соединение — «подвисания» API при «здоровых» серверах | Алерт → увеличить пул/добавить read-replica для чтений |
| Disk queue depth / IOPS у БД | > 90% лимита диска 10 минут | Диск — насыщенность, БД станет узким местом всего конвейера | Алерт high → расширение диска Managed БД (тикет + вызов on-call при повторе) |
| `orders_stuck` (застрявшие заказы) | > 10 заказов дольше SLA статуса | Прямой бизнес-сигнал «теряем заказы» — ради него всё и строится | Алерт critical → дежурный разбирает заказы по трейсам; уведомление продакту при > 50 |

Общий принцип: пороги привязаны к **пиковой** нагрузке (×2 от средней) и
SLA статусов заказа; реакция градуированная (тикет → алерт дежурному →
«звонилка» для critical по бизнес-метрикам), чтобы не приучать команду к
ложным срабатываниям.
