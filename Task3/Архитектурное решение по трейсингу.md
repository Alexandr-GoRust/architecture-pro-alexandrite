# Архитектурное решение по трейсингу

## 1. Анализ системы: где заказ может «сломаться» или зависнуть

Путь заказа: онлайн-магазин (`INITIATED → FILE_UPLOADED → SUBMITTED`) →
расчёт в MES (`PRICE_CALCULATED`) → подтверждение в CRM
(`MANUFACTURING_APPROVED`) → производство в MES (`STARTED → COMPLETED →
PACKAGING → SHIPPED`) → закрытие в CRM (`CLOSED`). B2B-сценарий: заказ
создаётся в CRM **получением сообщения из очереди** RabbitMQ.

Точки риска («заказ в непонятном состоянии»):

1. **Messages Queue (RabbitMQ)** — потеря, дубль или зависание сообщения между
   MES и CRM (главный подозреваемый в «не получили заказ»).
2. **Границы MES ↔ CRM** — смена статуса в одной системе не доехала до другой:
   заказ «застревает» в промежуточном статусе (`PRICE_CALCULATED` без
   подтверждения, `SHIPPED` без `CLOSED`).
3. **Расчёт стоимости в MES (2–30 минут)** — долгая операция без видимости:
   клиент и поддержка не знают, идёт расчёт или он упал.
4. **Shop API / CRM API** — приём B2B-запросов: таймауты и ошибки на границе
   «партнёр → API → очередь».

**Трейсингом покрываем: Shop API, CRM + CRM API, MES + MES API, Messages Queue**
(все контейнеры внутри «Jewerly Store System» и шина) — на диаграмме
`C4_tracing.drawio` они связаны новыми красными элементами.

### Данные, которые должны попадать в трейсинг

- `trace_id` и `span_id` для каждого перехода заказа между системами;
- атрибуты ресурса: `service.name` (shop-api / crm / mes), `env`, `host`;
- атрибуты спана: `order_id`, `customer_id` / `partner_id`, `order.status`
  (из/в), `message_id` очереди, `queue.name`, `endpoint`;
- длительность и результат каждого шага (включая время расчёта стоимости);
- события ошибок и ретраев вместе с контекстом запроса.

Контекст передаётся между сервисами через **заголовки HTTP/gRPC-запросов и
заголовки сообщений очереди** (context propagation) — так трейс склеивается в
одну цепочку через магазин, очередь, CRM и MES.

## 2. Мотивация

Команда видит заказы «в непонятном состоянии», а сообщения — теряются;
сейчас единственный инструмент разбора — со слов клиента. Трейсинг даст:

**Технические метрики (3–5):**
1. Время прохождения каждого статуса заказа (latency по спанам) — где именно
   заказ стоит дольше SLA.
2. Доля запросов с ошибками на каждом участке (error rate трейсов).
3. Время расчёта стоимости: распределение и хвосты (p95/p99) по сложности
   моделей.
4. Глубина и лаг обработки сообщений из трейсов очереди.
5. MTTR инцидентов «заказ пропал»: поиск по `order_id` в Jaeger за минуты
   вместо разбора логов всех серверов неделями.

**Бизнес-метрики:**
- Число «застрявших» заказов, обнаруженных раньше жалобы клиента.
- Доля B2B-заказов, прошедших путь без ручного вмешательства.
- Среднее время ответа партнёру «где мой заказ» (дни → минуты) — удержание
  контрактов.

## 3. Предлагаемое решение

**OpenTelemetry + Jaeger** — отраслевой стандарт телеметрии + зрелый бэкенд
трейсинга.

Компоненты (на диаграмме — **красным**):

- **SDK OpenTelemetry** в приложениях (Java: shop-api, crm — java-агент OTel
  с автоинструментацией Spring Boot; C#: MES/MES API — `OpenTelemetry.NET`,
  автоинструментация ASP.NET Core; клиент HTTP — пробрасывание контекста);
  инструментация RabbitMQ-клиентов — контекст в заголовках сообщений.
- **OpenTelemetry Collector** — приём спанов по OTLP от всех сервисов,
  фильтрация, батчинг, экспорт.
- **Jaeger** (collector + storage + Jaeger-UI) — хранение трейсов и поиск.
  Хранилище: Elasticsearch/OpenSearch (общий кластер с логированием из Task4);
  для старта допустим all-in-one в памяти на dev-окружении.

Схема: **`C4_tracing.drawio`** — доработанная диаграмма контейнеров; новые
элементы (OTel Collector, Jaeger) и связи «спаны OTLP» выделены красным.

Роли: Jaeger-UI и Collector разворачивает DevOps-инженер; инструментацию
Java-сервисов ведут два Java-разработчика, MES — C#-разработчик (по урокам
OTel это в основном автоинструментация + атрибуты заказов).

### Дополнительное задание: мониторинг пути заказа и алертинг из трейсов

На базе трейсов строится **Order Flow Monitor**: периодический анализ
завершённых/незавершённых трейсов пути заказа — время прохождения статусов
сравнивается с SLA, зависшие (без смены статуса дольше порога) и оборванные
(трейс без завершающего спана) заказы превращаются в алерты через
**Alertmanager** (Telegram/e-mail дежурному). Схема: **`C4_tracing_alerting.drawio`**
(новые элементы Order Flow Monitor, Alertmanager, дежурный инженер — **зелёным**).

## 4. Компромиссы

1. **Проприетарное наследие**: MES куплен с исходниками, но глубоко
   инструментировать чужой код дорого — ограничиваемся автоинструментацией
   HTTP/очередей и ключевыми спанами смены статусов; внутренние циклы расчёта
   стоимости остаются «чёрным ящиком» с длительностью на входе/выходе.
2. **Накладные расходы**: телеметрия добавляет единицы процентов CPU/RAM и
   трафик; на старте применяем сэмплирование (например, 100% ошибочных +
   10% успешных трейсов), полноту включаем по необходимости.
3. **Объём хранения**: трейсы дороже метрик; горячие трейсы — 14 дней, потом
   удаление/деградация детализации (ILM), иначе Elasticsearch вырастет в цене.
4. **Трейсинг не заменяет логи и метрики**: без логов (Task4) не видно деталей
   ошибки внутри спана, без метрик (Task2) — общей динамики; внедряем все три
   источника, трейсинг — второй по приоритету после метрик.
5. **Командные ресурсы**: команда не осилит всё сразу — порядок покрытия как в
   Task4: MES ↔ CRM ↔ очередь (где теряются заказы), затем Shop API, затем
   B2C-фронт.

## 5. Безопасность

- **Аутентификация и доступ**: Jaeger-UI, Collector и Order Flow Monitor —
  только внутри корпоративной сети (VPN), вход через корпоративный SSO;
  роли: «Поддержка» и «Разработка» — поиск/просмотр трейсов, «Администратор» —
  управление retention и сэмплированием. B2B-партнёры наружу трейсинг не видят.
- **Данные в трейсах**: атрибуты ограничены идентификаторами
  (order_id/customer_id/partner_id) — паспортные данные, реквизиты и содержимое
  3D-моделей в трейсы не пишутся (маскирование на уровне OTel-процессоров в
  Collector: `redaction`/attribute-фильтры).
- **Транспорт**: OTLP поверх TLS от сервисов к Collector и от Collector к
  хранилищу; интерфейс Jaeger-UI за reverse-proxy с TLS и SSO.
- **Аудит**: действия пользователей в Jaeger-UI (поиск, просмотр) логируются в
  общий контур логирования для расследования инцидентов ИБ.
