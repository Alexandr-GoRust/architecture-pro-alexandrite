# Архитектурное решение по логированию

## 1. Какие логи собирать и откуда

Сбор логов — из всех четырёх бэкенд-компонентов и интеграционной шины:
**Shop API (онлайн-магазин), CRM + CRM API, MES + MES API, RabbitMQ** (события
шлюза/очередей), плюс системные логи узлов EC2 и Managed БД. На схеме C4 — все
контейнеры внутри «Jewerly Store System» и Messages Queue.

### Обязательные события уровня INFO (ядро — путь заказа)

| Система | Событие (INFO) | Поля |
|---|---|---|
| Онлайн-магазин | Заказ создан (`INITIATED`) | время, order_id, customer_id, канал (сайт/конструктор) |
| Онлайн-магазин | Файл 3D-модели загружен (`FILE_UPLOADED`) | время, order_id, customer_id, file_id, размер, кол-во полигонов |
| Онлайн-магазин | Заказ отправлен (`SUBMITTED`) | время, order_id, customer_id |
| MES | Стоимость рассчитана (`PRICE_CALCULATED`) | время, order_id, длительность расчёта, статус расчёта |
| CRM | Заказ подтверждён (`MANUFACTURING_APPROVED`) | время, order_id, seller_id |
| MES | Заказ взят в работу/выполнен/упакован/отправлен (`MANUFACTURING_STARTED/COMPLETED`, `PACKAGING`, `SHIPPED`) | время, order_id, operator_id |
| CRM | Заказ закрыт (`CLOSED`) | время, order_id, источник (транспортная компания/вручную) |
| CRM / MES | Сообщение опубликовано в очередь / получено из очереди | время, order_id, queue, message_id, publisher/consumer |
| Shop API | B2B-запрос API принят/обработан | время, request_id, partner_id, endpoint, status |

Каждая запись о смене статуса обязательно содержит: **время, идентификатор
покупателя (customer_id/partner_id), номер заказа (order_id)** — как в примере
задания. В каждое сообщение также включаем `service`, `env`, `host` и
`trace_id` (после внедрения трейсинга) — это склеит логи с трейсами.

### Другие уровни

- **WARN** — нештатное, но восстановимое: некорректный входной файл (модель с
  аномальным числом полигонов), повторная доставка сообщения (дедупликация
  сработала), замедление расчёта сверх нормы, попытка операции при исчерпании
  пула соединений.
- **ERROR** — сбой обработки, требующий вмешательства: ошибка публикации в
  очередь, падение консьюмера, ошибка записи в БД,неудачный расчёт стоимости.
- **FATAL** — отказ компонента: JVM/C#-процесс умирает, недоступность БД/очереди.
- **DEBUG/TRACE** — только dev/release-окружения; на проде выключены, чтобы не
  засорять логи (включаем точечно на время диагностики).

## 2. Мотивация

Сейчас ошибки разбираются «со слов клиента»: разработчики и поддержка тратят
часы на поиск того, «что случилось на стороне сервиса». Централизованное
логирование даст:

**Технические метрики:**
1. Время локализации инцидента (MTTR): часы → минуты — ищем по order_id сразу
   во всех системах.
2. Доля инцидентов, разобранных без привлечения разработчика (поддержка сама
   по логам).
3. Полное покрытие пути заказа логами (100% смен статусов логируются).

**Бизнес-метрики:**
4. Число потерянных/зависших заказов, найденных логами раньше жалобы клиента.
5. Скорость ответа B2B-партнёрам на вопрос «где мой заказ» (дни → минуты) —
   прямое влияние на удержание контрактов.

### Приоритет внедрения логирования/трейсинга (команда не осилит всё сразу)

1. **MES и CRM + их обмен через RabbitMQ** — здесь теряются и зависают заказы
   (главная боль бизнеса), здесь же работает самый медленный процесс (расчёт
   стоимости 2–30 мин).
2. **Shop API** — B2B-контур: партнёры «ежедневно не получают заказы», нужно
   логирование приёма/обработки их запросов.
3. Онлайн-магазин (B2C-фронт) — последним: его здоровье частично видно через
   Яндекс Метрику, жалобы B2C-клиентов опосредованы менеджерами.

Трейсинг внедряем в том же порядке (см. Task3) — сначала MES↔CRM↔очередь.

## 3. Предлагаемое решение

**Стек ELK: Filebeat → Logstash → Elasticsearch ↔ Kibana.**

- **Filebeat**-агенты на каждом узле (EC2-инстансы приложений): следят за
  лог-файлами приложений (JSON-формат логов задаём в logback/log4j2 для Java и
  Serilog для C#), доставляют в Logstash. Для контейнеров — контейнерный сбор.
- **Logstash**: пайплайны под каждый источник: парсинг JSON, нормализация полей
  (`order_id`, `customer_id`, `service`, `env`, `trace_id`, `level`),
  обогащение (имя сервиса), маршрутизация по индексам.
- **Elasticsearch**: индексы вида `logs-{service}-{YYYY.MM.dd}` — **отдельный
  индекс (шаблон) под каждую систему**: разные retention и права доступа;
  ILM-политика управляет жизненным циклом (rollover по размеру/возрасту).
- **Kibana**: data view по каждому индексу, поиск по order_id/trace_id,
  дашборды «Путь заказа», «Ошибки по сервисам», «Очередь».

Схема: все новые компоненты и связи отражены на приложенной диаграмме
контейнеров (обновлённая C4).

### Политика безопасности логов

- В логи **не пишутся** чувствительные данные: паспортные данные, платёжные
  реквизиты, содержимое 3D-моделей; маскирование PII (e-mail, телефон) на
  стороне Logstash (filter) до записи в Elasticsearch.
- Доступ к Kibana — через корпоративную аутентификацию, роли: **Поддержка** —
  чтение business-индексов; **Разработка** — чтение + dev-индексы;
  **Администраторы** — полный доступ, включая управление ILM. B2B-партнёры
  доступа к логам не имеют.
- Kibana/ES не публикуются наружу (доступ только из внутренней сети/VPN),
  аудит обращений к дашбордам включён.

### Политика хранения

| Индекс | Хранение | Обоснование |
|---|---|---|
| `logs-mes-*`, `logs-crm-*`, `logs-rabbitmq-*` | 30 дней горячий + 60 тёплый (HDD) | Сроки гарантий для разбора инцидентов с заказами; логи работы сервиса — не дольше квартала |
| `logs-shop-api-*` (B2B) | 90 дней | Контрактные обязательства перед партнёрами по разбору инцидентов |
| Логи аудита смены статусов заказа | 1 год | Разбор спорных заказов/претензий клиентов |
| `logs-app-debug-*` (dev/release) | 7 дней | Отладочные, быстро теряют ценность |

Ожидаемый объём: ~1–2 ГБ/день на сервис (JSON-логи INFO-уровня) — шарды
10–50 ГБ, ILM rollover по 30 ГБ или суткам; полный кластер укладывается в 3
небольших узла Elasticsearch.

## 4. Превращение сбора логов в систему анализа

1. **Алертинг по логам** (Kibana Alerting / ElastAlert):
   - рост `ERROR`/`FATAL` по сервису за минуту (порог, например, >10);
   - появление `orders_stuck`-событий (заказ в статусе дольше SLA);
   - сообщение попало в DLQ — отдельный алерт дежурному.
2. **Поиск аномалий**: правило «резкий рост числа записей о создании заказов»
   (например, было ~4/сек, стало 10 000/сек) — маркер DDoS или бага партнёрской
   интеграции: алерт + автозапрос на блокировку источника через rate limiter.
   Аномалии в паттернах (доля статусов, распределение длительностей расчёта) —
   через ML-джобы Elasticsearch.
3. **Склейка источников**: общий `order_id`/`trace_id` в логах всех систем +
   дашборд «Путь заказа» превращают разрозненные записи в хронику одного
   заказа — тот самый «системный анализ», который сейчас делается вручную
   неделями.

## 5. Дополнительное задание: критерии выбора технологии

| Критерий | ELK (Elastic) | OpenSearch | Splunk | Loki (Grafana) |
|---|---|---|---|---|
| Лицензия | Elastic License (не OSS для облаков) | Apache 2.0 | Проприетарная | AGPL/Apache |
| Стоимость входа | Средняя: свой кластер, Free basic-уровень X-Pack | Средняя, полностью открытая; популярен в РФ | Высокая (платёж за объём данных) | Низкая: объектное хранилище, индексация только ярлыков |
| Полнотекстовый поиск | Отличный (инвертированные индексы, Lucene) | Отличный (форк ES) | Отличный | Ограниченный (поиск только по ярлыкам, потом grep) |
| Экосистема/сбор | Beats + Logstash, зрелые пайплайны | Совместим с Beats/Logstash | Universal Forwarder | Promtail/Agent, тесно с Grafana/Prometheus |
| Опыт команды и вендор-лок | Java-стек, широко известен | Отсутствие лицензионных рисков ES в РФ | Риск ухода вендора/санкции | Требует привыкания к ярлыкам; нужен Grafana (уже есть) |

**Выбор: OpenSearch** (форк Elasticsearch, лицензия Apache 2.0): сохраняем все
преимущества ELK-стека (Beats/Logstash, инвертированные индексы, Kibana-совместимый
Dashboards) без лицензионных ограничений Elastic и без стоимости Splunk.
Ограничение Loki (слабый полнотекстовый поиск) критично: наш основной сценарий —
поиск по order_id/customer_id и текстам ошибок по всем системам. В документе
выше «ELK» употребляется обобщённо; реализация — OpenSearch + OpenSearch
Dashboards, пайплайн Filebeat → Logstash сохраняется.
