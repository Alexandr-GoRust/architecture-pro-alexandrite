# Архитектурное решение по кешированию

## 1. Анализ: что имеет смысл закешировать

Симптом: дашборд MES (первая страница — список заказов в работе по статусам)
грузится долго; фильтр и пагинация не помогли. Операторам критичны **самые
новые** заказы (от них зависит вознаграждение), т.е. паттерн доступа —
многократное «горячее» чтение одного и того же списка + редкие записи (смена
статуса одним оператором). MES DB — единственный инстанс на чтение и запись:
каждое открытие дашборда — тяжёлый SELECT по растущей таблице заказов.

Кешируем:

1. **Список заказов в работе по статусам (дашборд MES)** — основной кейс:
   чтение тяжёлое и частое, изменения редки, кратковременная несвежесть
   (секунды) не критична и устраняется инвалидацией по событию.
2. **Справочник готовых элементов конструктора и каталог готовых изделий** —
   меняются редко, читаются всеми посетителями витрины (кандидат и на
   клиентское HTTP-кэширование).
3. **Результаты расчёта стоимости (после вычисления)** — по `order_id`:
   расчёт стоит 2–30 минут, а результат запрашивают повторно (клиент, CRM,
   партнёр API); кешируем как свершившийся факт.

Не кешируем: сам расчёт стоимости в процессе (уникальная тяжёлая операция на
стороне MES, она асинхронна), персональные корзины в активном редактировании
(быстро меняются), данные, которых нет в базе (нет источника для кеша).

## 2. Мотивация

- **Скорость для операторов**: первая страница из кеша за миллисекунды вместо
  тяжёлого SELECT — операторы мгновенно видят новые заказы и забирают их;
  пропускная способность производства (которая «готова к двукратному росту»)
  перестаёт упираться в дашборд.
- **Разгрузка MES DB**: единственный инстанс БД читает/пишет всё; снятие
  потока чтений дашборда снижает утилизацию и насыщенность (метрики USE из
  Task2 это покажут) и готовит БД к двукратному росту заказов.
- **Скорость ответа B2B/B2C**: кешированные результаты расчёта стоимости и
  справочники ускоряют повторные обращения (API-партнёры, витрина).

В кеширование включаем: Redis (серверный кеш списков и результатов расчёта) +
клиентское HTTP-кэширование для статики витрины (Cache-Control) — они
дополняют друг друга.

## 3. Предлагаемое решение

**Серверное кеширование в Redis, паттерн Cache-Aside** (+ клиентское
HTTP-кэширование статики витрины).

Почему серверное, а не клиентское: список заказов формируется на сервере из
БД и нужен многим операторам сразу — клиентский кеш каждого браузера не
снимает нагрузку с MES DB и не даёт единой картины «самых новых заказов»;
HTTP-кэширование оставляем только для статических ресурсов витрины.

Почему **Cache-Aside**:

- самый простой и распространённый паттерн — приложение проверяет кеш, при
  промахе идёт в БД и кладёт результат под ключом (быстро внедряется силами
  existing-команды Java/C# без доработки БД);
- **устойчив к сбоям кеша**: при недоступности Redis приложение падает в БД —
  дашборд продолжает работать (медленнее), это критично, ведь другой
  отказоустойчивости у MES пока нет;
- **модель данных в кеше может отличаться от модели БД** — кешируем готовый
  агрегат «список для дашборда» (статус + окно сортировки), а не строки
  таблицы, без сложных зависимостей консистентности.

Почему не другие паттерны:

- **Read-Through**: к БД обращается сам кеш — меньше кода в приложении, но
  настройка лежит на стороне БД/кеширующих серверов (нужны доработки и
  экспертиза, которых в команде нет), кеш-промах первого запроса остаётся, а
  при сбое кеша данных брать неоткуда (в отличие от Cache-Aside). Выигрыш
  для одного дашборда не окупает усложнение.
- **Refresh-Ahead**: асинхронное обновление популярных ключей до истечения
  срока — хорош для «горячего» списка, но требует безошибочной работы кеша и
  качественного мониторинга (по уроку), а устаревание секундного масштаба у
  нас и так закрывается инвалидацией по событию. Возможное развитие после
  стабилизации.
- **Write-Through / Write-Behind**: паттерны записи через кеш. Наша запись
  (смена статуса) редкая и простая; проводить её через кеш — усложнение без
  выгоды: в Write-Through клиент ждёт синхронного обновления БД, Write-Behind
  добавляет риск потери записи при сбое — недопустимо для статусов заказов.
  Запись идёт напрямую в MES DB, кеш инвалидируется.

Схема работы (полная sequence-диаграмма — `caching_sequence.png`,
исходник `caching_sequence.puml`):

- **Чтение дашборда**: MES API → `GET orders:in_work` в Redis; при попадании —
  мгновенный ответ; при промахе — SELECT из MES DB, `SET` с TTL 60с.
- **Смена статуса**: MES API → UPDATE в MES DB → publish `OrderStatusChanged`
  в RabbitMQ (для CRM) → `DEL orders:in_work` (и ключей затронутых списков) →
  ответ оператору; CRM-консьюмер обновляет свою копию.

## 4. Стратегия инвалидации кеша

Основная стратегия — **инвалидация по ключу, запускаемая программно событием
изменения** (смена статуса заказа → сброс ключа списка, в котором заказ
числился), плюс **временная (TTL 60 c)** как страховка от пропущенных событий.

| Критерий | По ключу + событие (выбрано) | Временная (TTL) | На основе запросов | На основе изменений (общая) |
|---|---|---|---|---|
| Свежесть «самых новых заказов» | Мгновенная: список сбрасывается в момент смены статуса | Задержка до TTL; оператор видит новые заказы ≤60 c | Зависит от активности пользователей | Мгновенная, но сбрасывает всё «подряд» |
| Объём сбросов | Точечный: только затронутые ключи | Не сбрасывает, ждёт истечения | Избыточный | Часто избыточный (весь кеш домена) |
| Нагрузка на БД | Минимум: перечитывается только инвалидированный список | Ровная, но при коротком TTL — частые промахи | Пики после запросов | Пики перечитывания |
| Сложность реализации | Средняя: событие уже публикуется в RabbitMQ — подписка/вызов уже есть в коде смены статуса | Минимальная | Низкая, но малоэффективна | Средняя |
| Риск устаревших данных | Низкий; TTL — предохранитель от потерянных событий | Средний (окно = TTL) | Средний | Низкий |

Почему не чистая временная: операторам важны именно новые заказы — окно в
минуту означает «чужой» заказ уже забрали; TTL 5–10 c превращает кеш в
генератор промахов под нагрузкой. Почему не «на основе запросов»: триггер —
активность пользователя, а не изменение данных (по опыту уроков — источник
лишних сбросов). «На основе изменений» без указания ключа избыточна: одно
изменение статуса сбрасывало бы кеш целиком.

Итог: событие смены статуса → сброс **ключей затронутых списков**
(`orders:{status}`) и при необходимости `calc:{order_id}` — программно, по
ключу; TTL 60 c — страховочный слой.

## 5. Дополнительное задание: альтернативные решения

| | Решение 1: Redis перед MES API (выбрано) | Решение 2: read-replica MES DB + кеш только справочников |
|---|---|---|
| Описание | Cache-Aside на Redis для списков дашборда и результатов расчёта; инвалидация по событию смены статуса | Тяжёлые чтения уводятся на реплику БД; в Redis кешируются только редкоменяющиеся справочники |
| Плюсы | Максимальный выигрыш в латентности (память vs SQL); снятие основной доли чтений с БД; быстрая реализация, не зависит от Managed-БД | Консистентность чтений выше (реплика); меньше логики инвалидации; запас прочности для любых отчётов, не только дашборда |
| Минусы | Лишний компонент (Redis) в эксплуатации; кеш требует мониторинга (hit ratio, память) | Репликация = дороже (второй инстанс Managed), lag реплики; латентность всё равно SQL-масштаба (десятки–сотни мс); дашборд при пике всё равно грузит реплику |

**Заключение**: выбираем **Решение 1** — оно решает проблему операторов
(мгновенный дашборд) и защищает единственную БД уже на текущей инфраструктуре,
реализуется за один-два спринта силами текущей команды. Решение 2 остаётся
следующим шагом по мере роста (оно есть и в плане Task1, инициатива И4): когда
заказов станет вдвое больше, read-replica добавит ёмкость чтений, а кеш уже
будет снимать с неё пиковую нагрузку дашборда.
